# 检索性能与正确性基准

日期：2026-08-06  
环境：Windows 本地、SQLite + sqlite-vec 0.1.9、3652张合成事实卡、1024维向量、预热5轮后记录80轮。该结果用于验证算法改动，不代表尚未测试的ARM64、1.5核容器实绩。

## 基准规模

- 卡片、FTS和向量行数：3652
- 数据库大小：43,991,040 bytes（约42.0MiB）
- 首次构建：12.85秒
- 基准脚本：`scripts/benchmark_retrieval.py`
- 最终报告：`work/benchmark_runtime_v6_allocator_proof/report.json`

## 优化结果

| 通道 | 平均 | P95 |
|---|---:|---:|
| 精确匹配 | 1.3ms | 1.8ms |
| 加权 BM25 | 11.1ms | 27.6ms |
| 中文三元组 | 3.6ms | 9.4ms |
| 1024维向量 | 7.4ms | 9.7ms |
| 带校区和人群过滤的向量 | 5.9ms | 7.8ms |
| 四路顺序合计 | 23.3ms | 49.1ms |
| 四路并行召回 | 14.5ms | 29.9ms |
| Top50装载与候选分配 | 1.5ms | 2.3ms |
| 完整本地检索前端 | 15.9ms | 31.7ms |

旧保守基线的四路顺序P95为122.7ms。当前实现为精确、BM25和三元组各保留一条专用只读连接，向量通道使用已加载sqlite-vec的主连接，并通过线程并行四路查询。单通道锁保证同一SQLite连接不会被两个线程同时操作；线上回答并发上限为2，因此最多同时存在8个本地召回任务。

每条连接使用4MiB页缓存上限、内存临时表和64MiB只读mmap。四条连接的页缓存预算上限约16MiB；mmap是虚拟地址映射且只读页可共享，不能把4×64MiB直接算作常驻内存。任一路异常时，程序先等待其余线程收尾，再令整次检索失败；关闭数据库时也会取得全部连接锁，避免关闭在途查询。

2个并发请求的额外压力检查共执行200次完整本地检索前端，结果没有不一致；双请求批次平均33.0ms、P95 58.1ms。该检查证明了当前共享连接、锁和候选分配的线程安全边界，但ARM64及CPU限额下的吞吐仍须在VPS只读验收阶段实测。

原实现先取全库向量Top50，再在普通 `cards` 表中过滤。该做法不仅多一次 JOIN，而且当符合校区或人群条件的卡排在全库第51名以后时会漏召回。测试用50张更近但不符合校区的卡稳定复现了该问题。

当前数据库 schema v2 将 `validity`、`campus`、`audience` 存为 sqlite-vec metadata，在KNN内部预过滤。校区和人群的“指定值或全校空值”条件合并为一次向量查询。过滤路径从平均约111.5ms降至29.2ms，同时消除Top50后过滤的召回缺口。

复核又发现生产卡允许把全局适用范围写为“全校”，而旧查询只把空字符串视为全局卡；这会令“凌水”等指定校区问题漏掉全校政策。当前四路过滤都同时接受空值和“全校”，查询规划同时固定受众为“本科生”并规范化常见校区名称。修正后带过滤向量两轮P95均低于36ms，未产生显著性能回退。

## 远程调用优化

本地召回只占百毫秒量级，首问主要耗时仍来自查询规划、Embedding、Reranker和回答模型。因此增加了：

- 5分钟、最多256项的上下文无关答案 LRU 缓存；
- 归一化问题键，标点差异可命中同一缓存；
- 相同问题并发时使用 single-flight，共享同一个在途模型请求；
- 有上下文的追问不使用答案缓存，避免错用其他会话语境；
- 只缓存完整通过证据门的成功回答，不缓存证据不足或系统异常。

RRF 仍生成Top50，随后只增加一次最多50行的卡片装载。固定预算分配器先给独立事实分配 primary；存在跨来源证据时，即使独立事实填满预算，也确定性保留最多1个 alternate，最后预留最多1张导航卡，总数始终不超过12。它修复了旧版“先截前24张再去重”在重复卡密集时饿死后续独立事实的问题；候选阶段P95为2.3ms，Reranker文档数和0.35门槛均未扩大。

模型请求仍是首问的主要耗时。当前多连接并行仅覆盖四个本地召回通道，不建立常驻自定义线程池；使用Python事件循环的默认线程池，应用层仍以并发2和有界队列控制总负载。
