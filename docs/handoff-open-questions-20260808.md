# 当前卡点与项目背景

生成时间：2026-08-08。给一位没接触过这个项目的专家看。
分支 `retrieval-selection-fix`，182 tests 绿，测试跑 `uv run --extra dev pytest`。

本文所有数字都是跑出来的。推断的地方会写明。

---

## 一、这是什么

大连理工大学商学院本科生 QQ 群的校园事务答疑机器人。**个人自用**，不是产品，
没有正式发布要求。

```
QQ/NapCat → NoneBot → 查询规划 → 四路检索(SQLite FTS5+trigram+sqlite-vec)
          → RRF 融合 → 候选分配 → Reranker → 回答模型 → 轻量校验 → QQ
```

离线侧（Luna）抓取官方页面、抽成知识卡、审核、构库；线上侧只读，不抓网页。
四个模型全部走大工网关（OpenAI 兼容）：`Qwen3.5-9B` 规划、`bge-m3` 向量、
`Qwen3-Reranker-8B` 精排、`Qwen3.5-35B-A3B` 回答。

### 产品口径（用户已明确，不需要专家推翻，但可以质疑）

- 允许模型在证据基础上忠实改写，**不要求逐字引用**
- 低置信度**直接发送**，不进人工队列，答错了群里指出再修卡
- 检索故障要如实暴露，不用模型常识假装检索成功
- 常规问题尽量 10 秒内

## 二、知识库的真实形态（这条决定其他一切）

```
总卡 3251 张
但正常提问（validity != 'historical'）只能检索到：
    navigation  301 张   ← 只有官方标题+URL，无正文
    fact         71 张   ← 有 evidence_quote，能作答
    合计        372 张
```

**这是一个 372 张卡的知识库，其中 81% 是"只能给链接"的导航卡。**

不是 3251。90% 的导航卡和 57% 的事实卡被标成 `historical`，对当前提问不可见。

导航卡的 historical 是 `pipeline/catalog.py` 按「发布年份 < 当年」机械判的，
而那批语料是学院新闻归档（公示、获奖、活动），判得大致正确。

## 三、这一轮做了什么（有前后数字）

起因是「奖学金怎么申请」答成了图书馆签到卡。根因不是原交接包判断的候选分配器，
而是 `StrongRetriever.retrieve()` 的 `if fact_cards:` 无条件优先级——导航卡只能
通过「证据面缺失」这个**失败分支**才有机会出场，而 73.5% 的标准答案是导航卡。

改成「精排置信档位 → 首阶段名次」的融合排序后：

```
离线夹具（对抗性 reranker，零网关）
  gold 排第一        3/200 (1.5%)  →  198/200 (99.0%)

固定评测 300 题（真实网关）
  answer_card_match_rate            0.655
  p95 延迟                          9.43s   （之前有 48 秒长尾）
  faculty 泄漏                      0       ← 硬安全门守住
  official_source_rate              1.000
```

同批还做了：导航配额 1→3、重试预算按在线/离线拆开、发布链拆
`build_code_sha256`/`runtime_code_sha256`（**改运行时代码不再需要重构库**）、
知识库补卡（活 fact 卡 28 → 71）。

## 四、卡点

### 卡点 1（最想听意见）：372 张卡的库，这套检索架构是不是过重了

系统按「几千张卡」设计：四路召回 → RRF Top50 → 候选分配器压到 16 张 →
远端 Reranker → 选卡。但**活库只有 372 张，其中能作答的只有 71 张**。

在这个量级下，一些别的做法变得可行，比如把全部 372 张卡的标题（约 1.5 万字）
直接放进模型上下文让它挑。这会省掉 embedding + rerank 两次远端调用
（实测各约 2 秒），也绕开下面卡点 2 的一大半。

我没做这个判断，因为它是架构级的取舍，而我这一轮一直在现有架构里修 bug。
**想听专家意见：在 372 张卡（且增长缓慢）的规模上，现在这套是不是杀鸡用牛刀？**

### 卡点 2：机器人不知道自己不知道

固定评测里 100 道负例，改之前**拒答率 0%**。问「本科生怎样申请夜间无人机
驾驶证」，它会找一张最像的卡编出办理流程。

我加了两道门，都是在 300 题上标定过的：

```
主题门     问题与首选卡的字符二元组重合率 < 0.05 就拒答
           （去掉"本科生/申请/办理"这类套话后计算，否则句式本身就能过线）
受众门     问题的服务对象明显不是本科生就拒答
           （判据是"谁在办这件事"，不是"提到了谁"——"本科生如何免试攻读
             研究生"必须放行）

60 题子集结果：
  out_of_scope       0/6  →  6/6   ✅
  faculty_boundary   0/6  →  6/6   ✅
  no_answer          0/8  →  0/8   ❌  ← 卡在这里
  正例命中           66%  →  70%   （未受影响）
  真损失             1 题（该题重合率 0%，本来也答不对）
```

**`no_answer` 这类拒不掉**，因为它们故意写成本科生口径 + 一个虚构名词：

```
本科生如何申请2027年春季去月球基地实习？
本科生申请2030年校级元宇宙创业基金需要哪些材料？
商学院本科生如何办理校内宠物饲养许可证？
```

受众门管不着（受众确实是本科生），主题门也拦不住——去掉套话后剩「月球/球基/
基地」，而向量通道是 k-NN，**不管多远都返回最近的 k 个**，总能找到一张"沾边"的卡
把重合率顶上去。

我判断再往上调主题门阈值不划算：标定显示每提高一档，被拒的正例都是**本来答对的**
真实问题（「大工食堂几点开放」对应的卡叫「校内食堂餐次与营业时间」，用词不同
而非主题不同）。

**想听意见：在一个 372 张卡的封闭知识库上，怎么判断"这个问题问的东西根本不在库里"？**
我能想到的方向是检查问题里的关键实体是否出现在候选卡中，但没做——怕误伤，
也怕又是一个需要标定的正则。

### 卡点 3：固定评测集是循环的，测不出检索质量

`work/evaluation_20260807.jsonl` 的 200 道正例，**问题文本 200/200 逐字等于
标准答案卡自己的 `standard_question`/`generated_questions`**，而这些字段进了索引。

所以 `recall_at_50` / `recall_at_5` 恒接近 100%，改什么都是绿的。只有
`answer_card_match_rate` 还有效。

我另建了 44 题非循环冒烟集（`evaluation/smoke_non_circular.jsonl`，带投毒验证过的
循环性检查），但它太小，而且期望值是主题关键词不是 gold card id。

**真实问法下的表现远低于评测集**：十题人工冒烟里 top-1 主题正确只有 5–6/10。

### 卡点 4：知识库补不动

按缺口清单（`docs/kb-coverage-gaps.md`）抓了两轮：

```
第一轮  1080 个来源  →  67 张卡  →  净可用增量 ≈ 0（抓的是学院新闻归档）
第二轮   142 个目标  →  40 张卡  →  净增量 5 张（fact + current）
```

第二轮已经对着缺口清单精准选源，契约全绿（9 道门 0 失败），但产出仍然很低。
主要损耗在：

- 办事大厅（ehall）**19 条全部无正文**——登录验证过，`visitService` 是事务
  办理入口，开放期内是表单、期外是"服务暂时不可用"，目录页全 404。
  **它是事务系统，从不承载"怎么办"的说明。**
- 微信公众号文章占抓取目标的 42%，但多为宣传稿，抽不出办事事实
- 抽出来的卡里 25/35 被判 historical（多数判得对，确实是某学年的具体安排）

18 个高频缺口主题里，仍有 11 个净增量为 0：选课退课、教务系统密码、绩点计算、
保研推免、四六级报名、在读证明、毕业论文、出国交换、宿舍调换、快递点、学费核对。

## 六、几个可能有用的细节

- **精排分数不可比**：`Qwen3-Reranker-8B` 在这个网关上，头部候选常在 0.005–0.03
  内，全量跨度 0.08–0.22。所以选卡用的是"置信档位"（差距 < 0.05 视为同档，
  由首阶段名次决定），而不是分数本身。
- **网关会渐进降速**：空闲 0.5–1.5s/次，持续请求后 5.3s，更久 25s；不发 429 而是
  排队。300 题评测必须题间节流（用了 6–8 秒）+ 断点续跑，中途挂了三次。
- **`fabricated_links = 375`** 是指标定义跟不上产品改动：导航回答从 1 条链接改成
  3 条后，每题多出的 2 条被记成"伪造"。真正的安全属性由
  `official_source_rate = 1.000` 保证（每条 URL 都属于被引用的卡，程序取的，
  模型碰不到）。
- **`answer_card_match_rate` 阈值 1.0 不现实**，但它只进 `quality_passed`，
  不挡 `activate`。
